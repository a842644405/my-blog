### 节点内存高使用率排查与处理指南

以下是各步骤的详细拆解：

#### 第一步：节点级宏观分析

目标：确认问题范围，排除节点级异常。

1. 

   **命令：`kubectl top node <节点名称>`**

   **作用**：查看节点**当前实时**的CPU和内存使用率。

   ```
   NAME                       CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
   js-1.25.216.92.176         5758m        14%    55821Mi          99%
   ```

   `MEMORY%`列明确显示使用率为99%，确认问题。

   **注意点**：此数据来自metrics-server，反映的是**当前瞬时值**。需结合监控图表看趋势。

2. 

   **命令：`kubectl describe node <节点名称>`**

   **作用**：分析节点资源分配详情和状态。

   **关键信息**：

   `Capacity`/ `Allocatable`：节点总容量和可分配给Pod的量。

   `Allocated resources`：已分配给Pod的资源总和（基于`requests`）。

   `Conditions`：节点的健康状况，重点关注 `MemoryPressure`是否为 `False`。

   **输出解读与注意点**：

   比较 `Allocatable`和 `Allocated resources`。如果 `Requests`总和已接近 `Allocatable`，说明节点“承诺”的内存已满，**即使实际使用不高，新Pod也无法调度至此**。

   如果 `Limits`总和远大于 `Allocatable`（例如您案例中的227%），说明**内存被严重超卖**，是高风险配置。

   `MemoryPressure: False`表示kubelet认为当前内存压力不大，但可能与 `kubectl top`的99%冲突，**以 `top`的实时数据为准**。

3. 

   **命令：`kubectl get events --field-selector involvedObject.kind=Node,involvedObject.name=<节点名称> --sort-by=’.lastTimestamp’`**

   **作用**：检查节点层面是否发生了OOM Killer等关键事件。

   **注意点**：搜索输出中的 `OOMKilling`关键字。如果出现，意味着系统内核已开始杀进程，情况紧急。

#### 第二步：Pod级深度定位

目标：找出消耗内存最高的具体Pod。

1. 

   **命令：`kubectl top pods -A --use-protocol-buffers`或 `kubectl top pods -A`**

   **作用**：列出所有Pod的实时资源使用。添加 `--use-protocol-buffers`可能提升性能，但如果无输出请使用后者。

   **排序与过滤**：结合 `grep`和 `sort`定位问题节点上的Pod：

   ```
   kubectl top pods -A | grep <节点名称> | sort -k4 -rn
   # 假设第4列是内存，按内存使用量降序排序
   ```

   **注意点**：您提供的 `mem.txt`就是此命令的输出。**重点关注排名前10-20的Pod**，它们通常是问题的直接原因。

2. 

   **命令：`kubectl describe pod <Pod名称> -n <命名空间>`**

   **作用**：分析具体Pod的配置、状态和事件。

   **关键信息**：

   `Containers`-> `Resources`-> `Limits/Requests`：对比配置值与 `top`中的实际使用值。**如果实际使用接近或超过 `limits`，可能引发容器OOM；如果 `requests`设置远低于实际使用，则是调度问题的根源**。

   `Events`：查看是否有 `OOMKilled`、`FailedScheduling`等事件。`OOMKilled`是内存过高的直接证据。

   **注意点**：`OOMKilled`的Pod会被重启，检查其重启次数：`kubectl get pod <Pod名称> -n <命名空间>`，看 `RESTARTS`列。

#### 第三步：容器/进程级分析

目标：进入“问题Pod”内部，定位是哪个进程或哪部分应用代码导致高内存。

1. 

   **命令：`kubectl exec -it <Pod名称> -n <命名空间> -- sh`**

   **作用**：进入目标Pod的容器。

   **注意点**：确保容器镜像包含 `sh`或 `bash`等shell。许多轻量级镜像（如scratch, alpine）可能没有，此时需用其他调试工具。

2. 

   **命令（在容器内执行）：**

   **`top`或 `htop`**：查看容器内进程的实时资源占用。

   **`ps aux --sort=-%mem | head -20`**：按内存使用率排序显示进程。

   **应用专用工具**：

   **JVM应用**：`jstat -gcutil <pid>`查看GC情况；`jmap -heap <pid>`查看堆内存（谨慎使用，可能触发STW）。

   **Go应用**：如果集成了pprof，可通过HTTP端点分析内存。

   **Python应用**：可使用 `objgraph`, `memory_profiler`等。

#### 第四步：原因总结与处理方案

基于以上排查，根本原因通常为以下几类：



| 可能原因            | 特征                                                         | 解决方案                                                     |
| ------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **1. Pod内存泄漏**  | 单个Pod内存使用随时间持续增长，重启后暂时恢复。              | 使用应用性能剖析工具定位代码问题，修复泄漏。                 |
| **2. 资源配置过低** | Pod实际使用接近或超过其 `limits`，频繁 `OOMKilled`。         | **调高 `limits`至合理值**（如实际峰值 + 20%）。              |
| **3. 调度失真**     | Pod `requests`设置远低于实际使用（如您案例中 `request 1Gi`，实际用 `6Gi`），导致多个“巨兽”Pod被调度到同一节点。 | **调高 `requests`至接近常态使用量**。这可能导致Pod因节点资源不足无法重启，需结合方案5。 |
| **4. 节点内存不足** | 所有Pod的 `requests`总和已接近节点 `Allocatable`，节点确实“满”了。 | **增加节点内存**或**扩容集群**。                             |
| **5. Pod分布不均**  | 其他节点空闲，但Pod因 `requests`配置不当或亲和性规则未被调度过去。 | **调整 `requests`后，手动驱逐Pod**：`kubectl drain <节点> --ignore-daemonsets --delete-emptydir-data`或单独删除Pod重建。**注意**：`drain`会排空节点，操作前需评估。 |
| **6. 系统组件异常** | `kubelet`, `docker`等进程自身内存泄漏。                      | 重启相应服务，或升级版本。                                   |

### 核心注意事项总结

1. **优先级**：先通过 `kubectl top`和 `describe`快速定位到问题Pod，再深入分析。

2. **区分 `requests`和 `limits`**：调度只看 `requests`，OOM看 `limits`。配置不当是大部分问题的根源。

3. **谨慎操作**：

   不要随意删除 `kube-system`命名空间下的系统Pod。

   驱逐或删除业务Pod前，务必**先调整其Deployment/StatefulSet的资源配置**，否则重建的Pod会因相同配置再次被调度到原节点。

4. **治本之策**：建立监控告警（如节点内存>80%），并**定期使用VPA（垂直扩缩容）建议或通过巡检，优化所有工作负载的 `requests`和 `limits`配置**，使其贴近实际使用。这是避免此类问题最有效的方法。
